Q13 & Q14: Scaling a Zomato-like App with Modules

Q13 & Q14

Explain in your own words (3–4 sentences) how splitting utility functions into separate files using imports and exports would help you scale a Zomato-like app as it grows from 2 to 20 features. Give one concrete example.

📝 Explanation in Own Words

When a Zomato-like app starts small with 2 features, all code can fit in one file. But as it grows to 20+ features like reviews, discounts, delivery tracking, and user profiles, a single file becomes very hard to maintain. Splitting utility functions into separate files using named and default exports means each feature has its own isolated module — changes to one file don't accidentally break another.

It also makes teamwork easier: one developer can work on orderUtils.js while another works on discountUtils.js without any conflicts. Any file that needs a utility just imports it — no copy-pasting code everywhere.

🍕 Concrete Example:

Suppose a discount calculation getDiscountedPrice() is used in the cart page, checkout page, and promotions page. Without modules, each file would have its own copy. If the discount formula changes (e.g. a ₹500 cap is added), you would need to update it in 3+ places — and likely miss one.

With modules, discountUtils.js exports the single source of truth. All other files import it. Update one file and every feature is fixed instantly.

📁 Example Folder Structure for a Scaled Zomato App

src/
├── utils/
│ ├── discountUtils.js ← getDiscountedPrice, applyCoupon
│ ├── orderUtils.js ← placeOrder, cancelOrder, getOrderStatus
│ ├── formatUtils.js ← formatPrice, formatDate, formatAddress
│ └── authUtils.js ← validateEmail, validatePassword
├── pages/
│ ├── cart.js ← imports from discountUtils, orderUtils
│ ├── checkout.js ← imports from discountUtils, formatUtils
│ └── profile.js ← imports from authUtils, formatUtils
└── main.js
