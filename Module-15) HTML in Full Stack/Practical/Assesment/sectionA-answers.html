Variable Declaration — var / let / const

Scenario: You are building a food delivery app where each restaurant's details — name, cuisine type, and minimum order value — must remain constant throughout the session, but the currently selected dish should be updatable as the user browses the menu.

Answer — Code

// Restaurant details stay CONSTANT throughout the session → const
const restaurantName  = "Spice Garden";
const cuisineType     = "Indian";
const minOrderValue   = 199;

// Currently selected dish CHANGES as the user browses → let
let selectedDish = "Paneer Tikka";

selectedDish = "Dal Makhani";   // ✔ allowed — let is reassignable

// restaurantName = "Biryani House"; // ❌ TypeError — const cannot be reassigned

Why each keyword?

  • const for restaurantName, cuisineType, minOrderValue — these must never change during the session. const enforces this at the language level; any accidental reassignment throws a TypeError immediately. It is also block-scoped, preventing leakage.
  • let for selectedDish — the user switches dishes while browsing, so the variable must be reassignable. let is block-scoped (unlike var which is function-scoped and hoisted) and avoids the classic var pitfall of silent undefined values.
  • var — never used in modern JS because of its function scope, hoisting behaviour, and re-declaration allowance, which makes bugs harder to catch.

Delivery Fee Engine — Conditional Logic

Scenario: Orders above Rs 500 qualify for free delivery; orders between Rs 200 and Rs 500 attract a Rs 40 fee; orders below Rs 200 attract a Rs 70 fee. Users flagged as 'VIP' always receive free delivery regardless of order amount.

Answer — Code

function getDeliveryFee(orderAmount, userType) {
  // VIP check FIRST — overrides everything else
  if (userType === "VIP") return 0;

  if      (orderAmount > 500)  return 0;
  else if (orderAmount >= 200) return 40;
  else                          return 70;
}

console.log(getDeliveryFee(600, "regular")); // 0  (above 500)
console.log(getDeliveryFee(350, "regular")); // 40 (200–500)
console.log(getDeliveryFee(150, "regular")); // 70 (below 200)
console.log(getDeliveryFee(100, "VIP"));     // 0  (VIP override)

Why strict equality === over ==?

We use userType === "VIP" because strict equality checks both value and type with no implicit coercion. With ==, JavaScript performs type coercion — e.g. 0 == false is true — which can introduce silent bugs. Since userType is always a string, === is both safer and more explicit.

Why condition order matters

The VIP check must come first. If the order-amount conditions run before the VIP check, a VIP user with a low-value order would be incorrectly charged Rs 70 before the VIP rule is ever reached. The most specific override must always gate first.

Menu Listing — for-of vs forEach

Scenario: All available dishes are stored in a JavaScript array. You need to display every dish name in the console and, separately, count how many dishes are marked as vegetarian.

Answer — Code

const dishes = [
  { name: "Paneer Tikka",    isVegetarian: true  },
  { name: "Chicken Biryani", isVegetarian: false },
  { name: "Dal Makhani",     isVegetarian: true  },
  { name: "Fish Curry",      isVegetarian: false },
  { name: "Aloo Paratha",    isVegetarian: true  },
];

// Task 1: Display all dish names — for-of
for (const dish of dishes) {
  console.log(dish.name);
}

// Task 2: Count vegetarian dishes — forEach + counter
let vegCount = 0;
dishes.forEach(dish => {
  if (dish.isVegetarian) vegCount++;
});
console.log("Vegetarian count:", vegCount); // 3

Practical difference: for-of vs forEach

For this scenario, for-of is used for displaying names (clean, readable) and forEach for counting (declarative, no early exit needed).

Cart Module — Reusable Tax Calculation Function

Scenario: The same tax calculation — 5% GST on food items and 18% GST on beverages — must run in the cart preview, the checkout summary, and the order confirmation screen.

Answer — Code (Function Declaration chosen)

// Function Declaration — hoisted, clearly named, reusable anywhere
function calculateTax(price, category) {
  const rate = category === "Beverage" ? 0.18 : 0.05;
  return +(price * rate).toFixed(2);
}

// Same function used in all 3 screens:
console.log(calculateTax(200, "Food"));      // 10.00 (5% GST)
console.log(calculateTax(150, "Beverage")); // 27.00 (18% GST)

Comparing all three function forms

Choice: Function Declaration — it is fully hoisted so it can be called anywhere in the file, has a clear name for readability, and is the standard pattern for shared utility functions used across multiple screens.

Place Order Button — Event Handling

Scenario: Clicking the "Place Order" button must validate that the user has selected at least one item and entered a delivery address; if validation passes it should display a confirmation message without reloading the page.

Answer — Code

// addEventListener — not inline onclick
document.getElementById("placeOrderBtn")
  .addEventListener("click", function(event) {
    event.preventDefault(); // prevents page reload if inside a form

    const address = document.getElementById("address").value.trim();
    const cart    = getCartItems();

    if (!address) {
      document.getElementById("error").textContent = "Please enter a delivery address.";
      return;
    }
    if (cart.length === 0) {
      document.getElementById("error").textContent = "Please add at least one item.";
      return;
    }
    document.getElementById("confirmation").textContent = "Order placed successfully!";
  });

event.preventDefault() — when is it necessary?

When the "Place Order" button is inside a form element, clicking it triggers the default browser form submission — causing a full page reload and wiping all state. event.preventDefault() cancels that default so our JS validation and UI update run instead. Without it, the confirmation message would never be seen because the page reloads immediately.

Why addEventListener over inline onclick?

  • Separates JavaScript from HTML (clean code)
  • Multiple listeners can be attached to the same element
  • Gives access to the full event object
  • Listeners can be removed later with removeEventListener

Restaurant List — Fetch API: async/await vs .then/.catch

Scenario: You are integrating a live restaurant list by fetching from a REST API. The UI must show a "Loading…" spinner while waiting, render the results when data arrives, and display a user-friendly error message if the request fails.

Answer — async/await (chosen approach)

async function loadRestaurants() {
  const statusEl = document.getElementById("status");
  const listEl   = document.getElementById("restaurant-list");

  statusEl.textContent = "Loading...";   // show spinner

  try {
    const response = await fetch("https://api.example.com/restaurants");
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    const data = await response.json();

    statusEl.textContent = "";
    data.forEach(r => {
      const li = document.createElement("li");
      li.textContent = r.name;
      listEl.appendChild(li);
    });
  } catch (error) {
    statusEl.textContent = "Failed to load restaurants. Please try again.";
  }
}

Comparison

Aspect.then() / .catch()async / await
ReadabilityNested callbacks / chainedReads like synchronous code
Error handling.catch() at the chain endtry/catch block — one place
Loading stateSet before .then(), reset insideSet before await, reset in try block
DebuggingStack traces hard to followStack traces match code structure

Choice: async/await — managing a loading state with two outcomes (success and failure) is much cleaner with a single try/catch block. The control flow is obvious, the loading indicator reset is in the right place, and the code is far easier to maintain.
